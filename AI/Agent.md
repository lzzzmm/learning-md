# Agent基础
观察周遭环境并作出行动已达到目的。可以通过机器学习以及获取知识提升自身性能的自主实体。

Agent = LLM（大模型） + memory（长期记忆（训练/RRF）和短期记忆（RAG）） + plannng skills（规划，拆解任务） + tool use（工具使用）

![2026-03-30-22-44-57.png](./images/2026-03-30-22-44-57.png)

代表产品：OpenClaw，cursor（agent类型很多，有开发程序的，有制作ppt的等等）

三大结构：
- 感知层
  - 输入口，获取多模态信息并转换
- 决策层
  - 思考中枢，负责决策、推理与规划
- 执行层
  - 输出端，调用工具与环境互动


AI对话管理：
- 人设注入：锁定顶端，固化专家人设，就是设定角色
- 记忆剪枝：定期压缩历史记录，剔除寒暄，保留关键结论

RAG（检索增强生成）： = 检索技术 + LLM 提示
- 向 LLM 提问一个问题，RAG 从各种数据源检索相关的信息，并将检索到的信息和问题注入到 提示词模板中，LLM 最后给出答案


Text-to-SQL：用人话提问，让AI自动帮你写出对应的SQL查询语句

多智能体协作：
- 上下级协同
  - 一个“领导”Agent负责：拆解任务、分配子任务、汇总结果，另外的负责执行
- 师生式协同
  - 一个Agent负责：指导、纠错、反馈，另外的负责执行
- 竞争式协同
  - 多个Agent独立思考，互相“辩论”或“竞争”，最终选出最优答案

## agent的工作流程

AI Agent = 能“动态生成和调整工作流”的系统

agent自主性程度
- 低自主性
  - 比如写一篇文章，让一个简单的agent生成一些网络搜索词，然后调用网络搜索引擎搜索，利用网络返回的搜索信息写一篇文章
  - 低自主是通过完全确定的步骤序列实现目标
- 半自主性
  - 比如写一篇文章，让LLM决定是进行网络搜索还是查找最近新闻来源，还是在网站存档中搜索最近的研究论文，执行搜索之后，让LLM决定抓取多少个网页，如果是pdf，调用函数或使用工具将pdf转化为文本，然后写出一篇文章。让LLM决定是否要反思和改进，甚至可以返回获取更多网页，最后输出结果。
  - LLM可以做出更多决定，甚至是执行的具体步骤，自主选择工具，但这些工具通常是预先定义好的
- 自主性
  - 更高自主性的agent甚至可以编写新的函数，创建它可以执行的新工具

任务分解：确定工作流中的各个步骤
任务分解怎么做：
- 确定目标：写一篇关于 X 的市场分析报告
- 列出应该执行的步骤，将目标拆成逻辑清晰的子任务
  - 规划文章结构
  - 搜索相关数据
  - 抽取关键信息
  - 写初稿
  - 复查 & 修正
- 把每个步骤变成可执行节点
  - 每个子任务都可以单独执行
  - AI 可以对完成情况进行评估
  - 可以选择调用不同工具来完成不同步骤

工作流程像是由许多基本模块组成
- 模型：大型语言模型，大型多态语言模型，其他人工智能模型（pdf转文本，文本转语音等）
- 工具：api、信息检索（从数据库获取数据）、代码执行工具


评估agent：
- 主观评估（LLM评估）
  - 比如对于生成文章，可以一个agent是生成文章，然后利用LLM对文章的评估作为评判标准：
  - ![2026-04-04-23-46-27.png](./images/2026-04-04-23-46-27.png)
- 客观评估 （用代码进行评估）
  - 比如可以自己编写代码作为评估：编写材料不希望出现某些词“竞争对手”，那么可以写代码统计这个词出现的次数，以这个作为评估标准

两种主要评估类型：
- 端到端：评估整个agent输出质量以及组件输出质量
- 层级评估：衡量单个步骤的输出质量

误差分析：除了上面的评估，还要检查中间输出（LLM的痕迹）以了解它在哪些方面不足


智能体设计模式：
- 反思
  - 反思模式让智能体自我评估并改进输出，不只是一次性生成结果，而是允许模型迭代检视和优化自己的答案或行为
  - 类似让llm生成代码，然后我们复制代码再加上一些提示词或调整方向又让llm优化
  - ![2026-04-05-00-25-09.png](./images/2026-04-05-00-25-09.png)
- 工具使用
  - LLM可以调用函数来完成工作
- 规划
  - 让智能体将复杂目标拆解成可执行步骤并按顺序执行，而不是试图一次性解决问题（智能体的工作，不是hard code）
- 多智能体协作

## 使用工具
LLM决定何时请求调用某个函数来执行某些操作，收集某些信息或执行其他操作。

一个训练好的模型，然后我们问现在几点，训练好的模型无法得知当前确切时间。但我们可以提供一个获取当前时间的函数给LLM调用，这时LLM就能回答当前的确切时间。

![2026-04-05-17-42-13.png](./images/2026-04-05-17-42-13.png)

![2026-04-05-18-00-37.png](./images/2026-04-05-18-00-37.png)


对于工具只不过是LLM可以调用的函数：
```
from datetime import datetime
def get_current_time():
  """Returns the current time as a string"""
  return datetime.now().strftime("%H:%M:%S")
```

![2026-04-05-18-11-10.png](./images/2026-04-05-18-11-10.png)

让LLM使用工具的过程（现代语法使用前的步骤）：
- 向LLM提供工具实现该功能，然后告诉LLM该功能可用
- LLM决定调用工具时，它会生成一个特定输出，让你知道你需要调用哪个LLM函数
- 你调用该函数，获取其输出
- 获取你刚刚调用的函数的输出结果并将输出结果返回给LLM
- LLM会利用这些信息继续进行下一步工作

严格上讲，LLM并不调用工具，LLM只是要求我们调用该工具，但在构建智能体工作流的开发中，很多人会直接说LLM调用了该工具，但从技术上并不是这样的。

## 构建agentic ai 技巧
设计端到端评估技巧：
- 一开始使用简单粗暴的评估方法
- 当发现 eval 指标和人类判断不一致时，这正是改进指标的机会。可以调整指标设计，让它更准确地反映人类偏好或真实质量。
- 找出模型比人类表现差的地方，用这些作为改进模型和评估指标的重点


误差分析：
- ![2026-04-06-00-06-57.png](./images/2026-04-06-00-06-57.png)
- 根据追溯每一个步骤生成的痕迹，研究agent中哪些组件对错误的影响最大
- 具体做法是：
  - 找出系统当前 最常见或最严重的失败模式
  - 根据这些失败模式，设定下一步优先改进的部分（比如改善某个组件、改善 prompt、加入新的检验机制等）


提高非语言模型性能（网络搜索，用于检索RAG的文本检索，代码执行，训练好的机器学习模型（语音识别，图像识别。。。）

- 更换组件
  - 网络搜索：更换搜索引擎
  - RAG：更换RAG服务供应商
- 改进提示语
  - 添加示例样本
- 尝试使用不同的LLM
- 分解任务，将任务分解成更小的步骤，可以拆分为生成步骤和反思步骤
- 对模型进行微调

# Agent Memory
## 基础 为什么需要记忆
无状态agent的问题：
- ai agent不会保留或回忆信息
- 无法完成一项长期任务
- 在不同会话之间不具备上下文感知能力
- 缺乏适应能力，提供给agent的任何信息在交互过程中不会更新或用于后续行动


会话记忆包含的内容（按顺序）
- 系统提示词
- 过往多轮互动内容
- 用户提示词

agent memory不同形式：
- 短期记忆
  - 语义缓存
    - 使用缓存机制，用“向量相似度”判断问题是否类似，从而复用历史答案，减少调用 LLM
  - 工作内存
    - 上下文窗口
      - LLM 一次“能看到的内容范围”
      - 包括
        - 当前对话的历史消息
        - 用户输入的内容
        - 系统提示
      - 有长度限制，超过就会忘记前面的内容
    - 会话级记忆
      - 在一个session中，系统额外保存的信息
      - 即使对话很长，这些信息可以被重新插入Prompt，或存储在数据库里
- 长期记忆= 知识（Semantic）+ 经历（Episodic）+ 技能（Procedural）
  - 程序记忆
    - 存储的是：技能、步骤、策略
    - e.g. “如何调用某个 API”  “解决问题的步骤流程”
    - 体现在Prompt模板，agent工作流，tool使用规则
  - 语义记忆
    - 存储的是：事实、概念、规则，不依赖具体经历
    - e.g. “北京是中国的首都”  “Python 是一种编程语言”
    - 通常存储在：向量数据库，知识库
  - 情景记忆
    - 存储的是：过去发生过的事件，有时间顺序，上下文
    - e.g. “昨天用户问了天气问题” “刚刚执行过一次工具调用失败”
    - 在ai中是用于对话历史总结

```
用户问题
  ↓
查语义记忆（知识）
  ↓
参考情景记忆（历史）
  ↓
调用程序记忆（如何做）
  ↓
生成答案

```


RAG流水线：
```
数据准备：
文档 → 切分 → embedding → 向量库

查询阶段：
用户问题
     ↓
转向量 embedding
     ↓
在不同记忆库中检索：
   - Semantic DB
   - Episodic DB
   - Procedural DB
     ↓
把检索到的内容拼接成 prompt
     ↓
LLM 生成答案
```

## 构建内存管理器
代理堆栈：一系列工具和技术共同作用，使人工智能代理能可靠地执行任务
- 应用层
  - agent与用户或业务系统的接口层
  - 用户交互界面，任务触发与调用入口
  - 场景：我们在网页上想agent提问
- 网关与连接层
  - 负责与外部系统，api，数据库的安全通信
  - api网关，身份认证，权限管理，数据源集成
- 编排层
  - 管理agent各个模块的协同和任务流程
- 推理层
  - agent做决策和规划的核心逻辑
- 工具层
  - 提供执行能力的插件或工具集
- 数据层
  - 存储、管理和提供 Agent 使用的数据
- 治理与可靠性层
  - 确保 Agent 的行为安全、可控、可靠
  - 审计与日志，使用策略和安全规则，可用性监控和错误处理
- 基础设施层
  - 底层计算、存储和运行环境
  - 云/服务器资源、容器化、集群管理、弹性伸缩、网络支持

情景工程：对输入到LLM中的信息进行优化选择和塑造的过程，以便其能够可靠地完成任务——同时还要充分考虑到情境窗口的限制以及模型的约束条件


内存工程：专注于为ai agent设计、构建和维护记忆系统。它涵盖了代理记忆的存储、检索、分类以及生命周期管理等方面
- 内存生命周期
  - 1、数据收集（Aggregation & Ingestion）
    - 从多个渠道收集原始数据
    - 来源包括应用输入、外部数据库、API 等
  - 2、表示与元数据增强（Representation & Metadata Enrichment）
    - 使用向量嵌入模型（Vector Embeddings）丰富信息或使用 LLM 扩展原始数据
    - 添加元数据：时间戳、意图、语义等
  - 3、存储（Storage）
    - 将信息保存到数据库或内存系统中
    - 支持短期上下文、中期模式和长期行为
  - 4、组织（Organization）
    - 对信息进行建模、索引和内部关系绘制
    - 指定时间、语义和关系索引方式
  - 5、检索（Retrieval）
    - 通过不同策略提取可操作的记忆
    - 方式包括文本搜索、向量相似度、图遍历
  - 6、推理与处理（LLM Inference, Processing & Reasoning）
    - 使用 LLM 或推理引擎处理检索到的记忆和上下文
    - 生成决策、响应或执行动作
  - 7、序列化与输出（Serialization & Output）
    - 将处理结果序列化
    - 可回写到内存或作为用户输出
  - 8、持续学习循环（Continuous Learning Cycle）
    - 内存反馈到 LLM
    - 推理结果成为新的记忆组件，形成闭环学习

## 用语义工具内存扩展代理工具的使用
大型语言模型如何感知工具以完成任务：
- LLM 本身不直接做具体操作，而是通过“请求工具”的方式让外部系统执行任务，然后再把结果反馈回来
- 大模型上下文有限，如果提供的工具太多，我们不可能把所有工具（名称，参数，描述。。。）都放进去
  - 解决：工具检索：![2026-04-06-18-46-33.png](./images/2026-04-06-18-46-33.png)
  - 另一种解决：记忆增强单元：![2026-04-06-18-48-40.png](./images/2026-04-06-18-48-40.png)

| 特性       | 记忆增强单元（Memory-Augmented Unit） | 工具检索机制（Tool Retrieval）     |
| -------- | ----------------------------- | -------------------------- |
| **存储位置** | 外部可读写记忆（Memory Bank）或类似笔记本    | 外部工具库（固定数据库）               |
| **内容**   | 历史调用经验、上下文相关工具信息、状态           | 工具描述、参数、类别等静态信息            |
| **访问方式** | LLM 学会**按需查询记忆**，有选择性地读写      | LLM 通过检索器/向量搜索从工具库中选出最相关工具 |
| **动态性**  | 高：记忆会随使用更新，记录历史、优化策略          | 低：工具库相对固定，主要根据任务匹配         |
| **使用场景** | 长期任务、多轮对话、学习经验积累              | 工具数量多、上下文有限时快速选工具          |


## 内存操作：提取、整合和自更新内存
事实上，我们有很多数据源（数据库、api的访问权限，MCP服务器，互联网），这些是潜在的上下文窗口组件和内容。但我们无法将所有内容都放在上下文窗口中。


上下文缩减：
- 上下文摘要
  - 通过LLM对历史对话/文档做总结，提取关键信息、结论、状态
- 上下文压缩
  - 不改变核心内容表达，只是“更紧凑地表示”
  - 常见方法：
    - 去掉冗余（重复句子、无关信息）
    - 关键词提取
    - 编码压缩（如embedding、token压缩）
    - 结构化表示（JSON、表格）

循环代理：“执行 → 获取结果 → 判断 → 再执行”的循环过程

- 1.1、构建上下文

- 1.3、LLM采取行动（调用函数）

# LangChain框架
## 认识LangChain
LangChain的产品：
- Deep Agents:最高层应用封装（Agent 产品级）
- LangChain:自定义代理的构建模块，有基础组件，搭积木一样，底层依赖于LangGraph
- LangGraph：更底层，自定义agent开发每一个环节

LangChain核心组件：
- 语言模型 model：GPT，deepseek
- 提示管理 Prompt
- 链 Chain：允许将多个组件（语言模型，提示模板，记忆等）串联起来，形成一个工作流
- 记忆 Memory：保存对话历史或上下文信息，方便在后续对话中使用
- 代理 agent：工具用户输入自动选择和执行不同的操作
- 工作 tool：内置的功能模块，比如文本处理工具，数据查询工具等

## 记忆
![2026-04-19-13-10-43.png](./images/2026-04-19-13-10-43.png)

分类：
- 短期记忆：当前任务或会话的上下文
  - 对话历史
  - 查询结果
  - 任务状态
- 长期记忆：跨任务或会话的检验与知识
  - 知识库
  - 用户偏好
  - 失败经验

### 短期记忆
LangChain中短期记忆通过AgentState实现，会话历史（消息列表）是AgentState的一部分

LangChain提供Checkpointer对象保存AgentState, 每一次用户与AI的交互都会生成一个快照记录为一个checkpoint。同一会话的多个checkpoint形成一个组，用同一个thread_id标记

### 记忆管理策略
多轮对话导致历史消息越来越多，最终超出模型上下文限制（Deepseek不能超过128k），LangChain提供一些记忆管理策略来解决这个问题
- 修剪：拿到消息历史后，先移除前N条或后N条消息，再调用模型
- 删除：永久删除AgentState快照
- 总结摘要：先总结历史消息中早期消息，得到消息摘要。然后用消息摘要和最近的消息形成消息列表，再调用模型
- 自定义：自定义策略，例如工具用户问题筛选历史消息
